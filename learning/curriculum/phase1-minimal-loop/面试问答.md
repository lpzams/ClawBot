# Phase 1: 最小执行链 - 面试问答

## 常见面试问题

### Q1: 介绍一下你的 ClawBot 项目

**标准回答（90 秒）：**

"ClawBot 是我为了深入理解 AI Agent 底层机制而开发的学习项目。

**背景：** 现在的 Agent 框架比如 LangChain 封装了很多细节，我想从零实现一遍，理解模型、工具、状态、安全这些核心概念是如何协作的。

**第一阶段我实现了最小执行链：** 用户输入 → Harness 边界校验 → 消息组装 → 模型调用 → 结果验证 → 输出。

**核心设计：** 我采用了依赖注入，Harness 只依赖一个 `messages -> string` 的可调用协议，不绑定具体模型。这样测试时可以注入 Fake Model，实现确定性测试；生产时注入真实 API adapter。

**技术价值：** 这个设计让我理解了依赖倒置原则的实际应用，也让项目可以完全离线测试，不消耗 API 额度。项目有完整的单元测试和 TDD 开发过程。

**成果：** Phase 1 用 200 行代码实现了可测试的执行链，测试覆盖率 100%，零外部依赖。"

**如果只有 30 秒：**

"ClawBot 是我从零实现的 AI Agent Harness 学习项目。我用依赖注入设计了模型抽象层，通过 Fake Model 实现确定性测试，整个 Phase 1 用 TDD 方法完成，可以完全离线运行。"

### Q2: 为什么选择从零开发，而不是用现成框架？

**回答：**

"有两个原因：

**学习深度：** 用框架可以快速出结果，但会错过很多底层细节。比如 LangChain 封装了消息组装、模型调用、工具执行，我用它可以很快做出 Agent，但不一定理解 Harness 为什么需要状态管理、为什么需要最大步数限制、工具白名单怎么设计。从零实现一遍后，这些概念都变成了我亲手解决的问题。

**面试价值：** 面试时讲'我用了 LangChain'和讲'我实现了一个 Harness，采用了依赖倒置原则，参考了 Netflix Chaos Engineering'，深度完全不同。第二种展示了我对架构设计和工程实践的理解。

**平衡：** 当然，生产项目我会优先用成熟框架，避免重复造轮子。ClawBot 是学习项目，目标就是'造一遍轮子，理解轮子为什么这样造'。"

### Q3: 什么是依赖注入？为什么用它？

**回答：**

"依赖注入就是把依赖项从外部传入，而不是在内部创建。

**没有依赖注入的代码：**
```python
class Harness:
    def __init__(self):
        self.model = OpenAIModel()  # 硬编码，耦合
```

**用依赖注入：**
```python
class Harness:
    def __init__(self, model):
        self.model = model  # 从外部注入
```

**好处：**
1. **可测试性** - 测试时注入 Fake Model，不需要真实 API
2. **灵活性** - 可以切换不同的模型实现，不改 Harness 代码
3. **职责清晰** - Harness 专注消息编排，不关心模型从哪来

**在 ClawBot 中的应用：**
- 测试：`Harness(fake_model)`
- CLI：`Harness(OpenAICompatibleModel.from_env())`
- 未来可以注入本地模型、缓存包装器、限流装饰器等

这是依赖倒置原则（SOLID 中的 D）的实际应用。"

### Q4: 什么是 Fake Model？为什么需要它？

**回答：**

"Fake Model 是一个返回固定内容的测试替身（Test Double），用来替代真实模型 API。

**实现：**
```python
def fake_model(messages):
    return f'Fake: {messages[-1][\"content\"]}'
```

**为什么需要：**

1. **确定性** - 真实模型每次返回可能不同，Fake Model 返回固定，可以写确定性断言
2. **免费快速** - 不消耗 API 额度，不需要网络，测试秒级完成
3. **测试重点** - 我们要测试的是'Harness 是否正确组装了消息'，不是'模型质量好不好'

**实际效果：**
- ClawBot 有 7 个单元测试，全部用 Fake Model
- 运行时间 0.001 秒
- 任何人 clone 项目后无需 API Key 就能跑测试
- CI/CD pipeline 不需要管理密钥

这个设计思想借鉴了 Uber Michelangelo 平台对模型服务的抽象 - 测试时用 Mock 预测服务，生产时用真实模型。"

### Q5: 介绍一下 TDD（测试驱动开发）在项目中的应用

**回答：**

"ClawBot 的 Phase 1 严格采用了 TDD 的红-绿-重构循环。

**步骤 1：红灯（先写失败测试）**
```python
def test_run_agent():
    result = run_agent('hello', fake_model)
    assert result == 'Fake: hello'
```
运行 → `ModuleNotFoundError` → 这是预期的失败 ✅

**步骤 2：绿灯（最小实现）**
```python
def run_agent(prompt, model):
    messages = [{'role': 'user', 'content': prompt}]
    return model(messages)
```
运行 → 测试通过 ✅

**步骤 3：重构（改进设计）**
- 添加空输入校验
- 添加 system prompt 支持
- 提取 Harness 类
- 测试继续通过 ✅

**好处：**
1. **证明功能不存在** - 红灯确保测试真的在测试，不是假通过
2. **最小实现** - 避免过度设计，只写通过测试需要的代码
3. **重构安全** - 有测试保护，可以放心改进设计

**开发日志中的记录：** 项目文档中完整记录了这个过程，包括第一次红灯的 error 信息，可以展示给面试官看。"

### Q6: 项目中遇到的最大挑战是什么？

**回答（STAR 方法）：**

"**Situation:** 在设计模型抽象时，我纠结是用抽象基类（ABC）还是简单的可调用协议。

**Task:** 需要在'类型安全'和'简单实用'之间权衡。

**Action:** 我分析了两种方案：

方案 A - 抽象基类：
```python
class ModelInterface(ABC):
    @abstractmethod
    def call(self, messages: List[Message]) -> str:
        pass
```
优点：类型检查强、IDE 支持好
缺点：Fake Model 需要继承、样板代码多

方案 B - 可调用协议：
```python
Model = Callable[[List[Message]], str]
```
优点：简单、符合 Python duck typing
缺点：类型检查弱一些

我最终选择方案 B，原因：
1. Python 生态更推崇 duck typing
2. Fake Model 只需要一个函数，不需要类
3. 符合'最小实现'原则

**Result:** 这个决定让代码简洁很多，而且 Python 3.9+ 的 type hint 仍然能提供足够的类型提示。这个经历让我理解了'不要过度设计'的重要性。"

### Q8: 这个项目用到了哪些设计模式？

**回答：**

"主要用到三个：

**1. 依赖注入（Dependency Injection）**
- `Harness.__init__(self, model)` - 从外部注入依赖
- 实现了控制反转（IoC）

**2. 策略模式（Strategy Pattern）**
- 不同的 model 实现（Fake / Real）可以互换
- `Harness` 不关心具体是哪个策略

**3. 适配器模式（Adapter Pattern）- Phase 2**
- `OpenAICompatibleModel` 把供应商 API 适配成统一协议
- Harness 只知道 `messages -> string`，不知道底层是 HTTP 还是 SDK

**没有用但面试可能问的：**

**为什么不用工厂模式？**
- 当前只有两种模型（Fake / OpenAI），直接注入更简单
- 如果未来有 5+ 种模型，再考虑工厂

**为什么不用单例模式？**
- Harness 应该可以创建多个实例（不同 system prompt）
- 单例会限制灵活性

**关键：** 不是为了用模式而用模式，而是自然地解决了问题，事后发现'哦这就是某个模式'。"

## 技术深度问题

### Q9: 如何保证消息格式的正确性？

**当前实现：**
```python
messages = [
    {"role": "system", "content": system_prompt},
    {"role": "user", "content": prompt}
]
```

**可能的问题：**
- 拼写错误（`"roll"` 而不是 `"role"`）
- 缺少必需字段
- 类型错误（content 不是字符串）

**解决方案（由简到繁）：**

1. **类型提示**（当前）
```python
Message = Dict[str, str]
```

2. **运行时校验**（Phase 3）
```python
def validate_message(msg):
    if "role" not in msg or "content" not in msg:
        raise ValueError("Invalid message format")
```

3. **使用 dataclass**（未来）
```python
@dataclass
class Message:
    role: str
    content: str
```

4. **使用 Pydantic**（生产环境）
```python
class Message(BaseModel):
    role: Literal["system", "user", "assistant"]
    content: str
```

**权衡：** ClawBot 当前用方案 1，因为消息结构简单。生产环境建议方案 4。

### Q10: 如何测试 Harness 的错误处理？

**示例：**
```python
def test_empty_prompt_raises_error():
    harness = Harness(fake_model)
    with pytest.raises(ValueError, match="cannot be blank"):
        harness.run("   ")
```

**要测试的错误场景：**
- ✅ 空输入
- ✅ model 不可调用
- ✅ model 返回非字符串
- ⏳ model 抛出异常（Phase 2）
- ⏳ 超时（Phase 2）
- ⏳ 超过最大步数（Phase 3）

**测试原则：**
- 错误信息要清晰（告诉用户哪里错了）
- 异常类型要准确（ValueError vs TypeError）
- 敏感信息不出现在错误中（不泄露 API key）

### Q12: 你如何平衡代码质量和开发速度？

**回答：**

"在 ClawBot 中我的原则是：

**质量不妥协的：**
- 每个功能都有测试
- 边界校验（空输入、类型检查）
- 清晰的错误信息

**可以延后的：**
- 性能优化 - 先保证正确，再考虑快
- 全面的文档 - 核心 API 先文档，内部实现可以后补
- 完美的抽象 - 先用简单的，有需求再重构

**实例：**
Phase 1 我没有加入工具系统，虽然我知道最终需要。因为先把消息编排做对更重要，提前加工具反而会分散注意力。

**结果：**
Phase 1 用 3 天完成，代码量 200 行，测试覆盖 100%。没有技术债，因为该做的质量保证都做了；也没有过度设计，因为没做暂时用不到的功能。"
