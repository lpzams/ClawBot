# 面试准备 Skill

帮助你把 ClawBot 项目经验转化为简历内容和面试回答，结合企业案例让你在面试中脱颖而出。

## 工作流程

### 1. 读取学习成果

从 `learning/state.json` 和各 workbook 中提取：
- 已完成的 Phase
- 学习过的企业案例
- 完成的练习
- 掌握的技术概念

### 2. 生成面试材料

为每个已完成的主题生成：
- **简历描述**（30-50 字）
- **项目介绍**（1-2 分钟口述）
- **技术亮点**（深度技术问题的回答）
- **企业案例关联**（展示行业认知）
- **常见追问**（提前准备答案）

### 3. 模拟面试

提供常见面试问题，评价你的回答：
- 行为面试（STAR 方法）
- 技术面试（系统设计、代码实现）
- 场景面试（如何解决特定问题）

### 4. 优化建议

针对你的回答给出：
- 结构是否清晰
- 技术深度是否足够
- 是否突出亮点
- 如何简化或深化

## 使用方法

**生成简历描述：**
```
/interview-prep 简历
```

**准备项目介绍：**
```
/interview-prep 项目介绍
```

**模拟技术面试：**
```
/interview-prep 技术面试 phase2-adapter
```

**查看企业案例话术：**
```
/interview-prep 案例 netflix
```

**完整面试准备：**
```
/interview-prep 全面准备
```

## 输出格式

### 简历描述模板

```markdown
## ClawBot - AI Agent Harness 学习项目

**简历一句话：**
> 设计并实现了支持多模型供应商的 AI Agent 执行框架，采用适配器模式实现模型抽象，通过测试替身确保离线可测试性

**技术栈：**
Python 3.11+ | Agent Loop | Adapter Pattern | TDD | CI/CD (Jenkins)

**核心亮点：**
- 实现了 Harness 核心执行器，支持任意 `messages -> string` 协议的模型
- 采用依赖注入和 Fake Model 实现无网络依赖的确定性测试
- 参考 Netflix Chaos Engineering 设计了最大步数限制和工具白名单
- 建立 Jenkins Pipeline 实现自动测试和持续交付
```

### 面试问答模板

```markdown
## 常见问题 1：介绍一下这个项目

**回答框架（90 秒）：**

"ClawBot 是我为了深入理解 AI Agent 底层机制而开发的学习项目。

**背景：** 市面上的 Agent 框架比如 LangChain 封装了很多细节，我想从零实现一遍来理解模型、工具、状态、安全这些核心概念是如何协作的。

**核心设计：** 我把项目分成三层：
1. Harness 层 - 负责消息编排和边界校验，不绑定具体模型
2. Adapter 层 - 处理不同模型供应商的 API 差异
3. 业务层 - CLI、Web 或定时任务，只关注输入输出

**技术亮点：** 我采用了依赖倒置原则，Harness 只依赖一个 `messages -> string` 的可调用协议。这样测试时可以用 Fake Model 替换真实 API，实现确定性测试。这个设计思想类似 Uber Michelangelo 平台对模型服务的抽象。

**成果：** 项目有完整的单元测试、文档和 CI/CD pipeline，可以作为框架被其他 Python 项目直接导入使用。"

**如果面试官追问技术细节：**
- 为什么不用抽象基类？→ Python duck typing + 避免过度设计
- 如何保证安全？→ 最大步数、工具白名单、参数校验
- 测试覆盖率如何？→ 核心路径 100%，只用标准库 unittest
```

### 企业案例关联模板

```markdown
## Netflix Chaos Engineering 关联

**面试中这样讲：**

面试官："你在项目中如何处理 AI Agent 的可靠性？"

你："我借鉴了 Netflix Chaos Engineering 的思想。Netflix 用 Chaos Monkey 主动制造故障来测试系统韧性，我在 ClawBot 中也采用了类似理念：

1. **假设失败会发生** - 设置 `max_steps` 防止模型陷入无限循环
2. **限制爆炸半径** - 工具白名单确保即使模型行为异常也不会造成破坏
3. **可测试的失败** - Fake Model 可以模拟各种异常场景，不依赖真实 API

这套设计在实际使用中很有效，而且让我对分布式系统的容错设计有了更深的理解。"

**为什么这样讲有效：**
- ✅ 展示了对知名企业技术实践的了解
- ✅ 说明了具体的技术对应关系
- ✅ 强调了实际效果和个人收获
```

4. 提供一致的 STAR 方法指导

## 注意事项

1. **真实性第一**：只讲你真正理解和实现的部分
2. **数据支持**：用具体数据（测试数量、代码行数等）增强可信度
3. **企业案例准确**：确保引用的企业案例是可验证的公开信息
4. **STAR 方法**：行为面试问题用 Situation-Task-Action-Result 结构
5. **准备追问**：每个回答都预想 2-3 个可能的追问
